# Muse 並走トライアルの指示(7日間)

以下をそのまま Muse に渡して使います。開始日と終了日だけ書き換えてください(案: 2026-11-19〜2026-11-25)。

---

このリポジトリ(briefings-daily-news)で、日次ブリーフィングの生成を引き継げるかを確かめる7日間の並走トライアルを行ってください。期間は **{開始日}〜{終了日}** の連続7日です。

## 目的

2026-11-17 のデモ版の評価(`drafts/2026-11-17-briefing-muse-review.md`)で、形式と要約の正確さは合格水準でした。分かっていないのは次の2つです。このトライアルはそれを確かめます。

- 毎朝、決まった時刻に、人の操作なしで完走できるか
- その日の主要な記事を落とさず、すでに載せた話題を繰り返さずに選べるか

## 毎日やること

毎朝 **06:30 JST に開始し、06:55 JST までに push** してください(公式版は 07:02 に別の仕組みが生成します。それより前に終えることが条件です)。

1. 日付は必ず日本時間で求める: `TODAY=$(TZ=Asia/Tokyo date +%Y-%m-%d)`。以降の `date` もすべて `TZ=Asia/Tokyo` を付ける
2. `git pull --rebase origin main`
3. `CLAUDE.md` と `cowork/SKILL.md`・`SOURCES.md`・`SELECTION_RULES.md`・`TEMPLATE.md`・`DENYLIST.md` に従って、その日のブリーフィングを作る。ただし保存先と、下の「今回の追加ルール」が優先
4. 保存先は **`drafts/muse-trial/${TODAY}-briefing-muse.md`**。タイトルは `📅 YYYY-MM-DD デイリーブリーフィング（muse トライアル）`
5. `bash cowork/scripts/check.sh drafts/muse-trial/${TODAY}-briefing-muse.md` を実行する。FAIL なら直して再実行し、PASS になってから先へ進む。実行した回数と、各回の出力を控える
6. `drafts/muse-trial/run-log.md` の末尾に、その日の記録を追記する(書式は下)
7. その日のブリーフィングと `run-log.md` だけを `git add` し、コミットメッセージ `YYYY-MM-DD briefing muse trial` で commit して `git push origin main`

## やってはいけないこと

- `_posts/` への追加・変更(公開されます。トライアル中は絶対に触らない)
- `cowork/`・`_layouts/`・`assets/`・`.github/`・`_config.yml`・`CLAUDE.md` の変更
- 当日の公式版(`_posts/${TODAY}-briefing.md`)を待つ・読む・参考にすること(06:55 までに終えれば存在しません。もし存在していたら、読まずに `run-log.md` に「公式版が先に存在」と書く)
- 画像の生成(`SKILL.md` Step 4.6)と、カレンダーへの通知(Step 7)。今回は対象外
- 人に確認や承認を求めて待つこと。承認が必要になったら、その事実を `run-log.md` に書き、その日は「未完走」として終える(無人で走れるかを見ているため)

## 今回の追加ルール(デモ版の評価で出た改善点)

### 1. 過去に載せた記事・話題を繰り返さない

- URL は、末尾の `/`・`?` 以降・`#` 以降を取り除いてから、`cowork/cache/past_urls.txt`(同じように整えたもの)と比べる。check.sh は末尾の `/` の違いは区別しなくなった(2026-11-17 に修正。デモ版では ChatGPT Wallet の記事がこの違いだけで通ってしまった)が、`?` 以降と `#` 以降は今も見ないので、PASS しても重複が残ることがある
- 自分がこのトライアルで前日までに載せた URL(`drafts/muse-trial/*-briefing-muse.md`)も、載せ済みとして扱う
- 話題でも照合する。候補ごとに、社名・製品名・CVE 番号で直近7日の `_posts/` と `drafts/muse-trial/` を検索し、同じ出来事がすでに載っていたら採用しない(例: 月例パッチのベンダー報道と IPA の注意喚起は同じ出来事)
- 新しい展開がある続報だけは採用してよい。その場合は要約の1文目に、前回から何が新しいかを書く

### 2. 主要信頼ソースをすべて当たる

`SOURCES.md` の主要信頼ソース16個を、毎日すべて確認する(日経新聞、NewsPicks、TechCrunch、OpenAI Blog、Google Research Blog、Anthropic Blog、Hacker News(AI)、Hacker News(Show HN / Launch HN)、Product Hunt、DevelopersIO、窓の杜、Publickey、LeadDev、InfoQ、The Hacker News、IPA)。ソースごとに、7日以内の候補が何本あったかを `run-log.md` に書く。読めなかったソースは「取得不可」と理由を書く。

### 3. 新しい記事を優先する

公開から2日以内の候補がある欄では、それより古い記事を選ばない。3日以上前の記事を採用するのは、その欄に新しい候補がなく、過去にも載せていない場合だけ。

### 4. 1つの欄を1つのソースで埋めない

- AI 最新動向: 同じ会社の自社発表は2本まで
- セキュリティ: The Hacker News に加えて IPA も確認する
- 「本日の更新なし」と書くのは、その欄のソースをすべて当たって候補が0本だったときだけ

### 5. 要約は記事の説明ではなく事実を書く

「〜を整理した記事」「〜をまとめた週次記事」のように記事の種類を説明する書き方をしない。何が変わったか・いくらか・いつからか・誰がかを書く。有料で本文が読めない記事は、公開の範囲で確かめられた事実だけを書く。確かめられないなら採用しない。

## run-log.md の書式(毎日、末尾に追記)

```markdown
## YYYY-MM-DD

- 開始 / 終了(JST): HH:MM / HH:MM
- push したコミット: (ハッシュ)
- 完走: はい / いいえ(いいえの場合は理由)
- 人の操作・承認: 0回 / N回(何に対して)
- check.sh: N回実行。1回目の結果(PASS / FAIL の行をそのまま)、最終結果
- ソース別の候補数(7日以内 / うち2日以内):
  - 日経新聞: n / n
  - NewsPicks: n / n
  - TechCrunch: n / n
  - OpenAI Blog: n / n
  - Google Research Blog: n / n
  - Anthropic Blog: n / n
  - Hacker News(AI): n / n
  - Hacker News(Show HN / Launch HN): n / n
  - Product Hunt: n / n
  - DevelopersIO: n / n
  - 窓の杜: n / n
  - Publickey: n / n
  - LeadDev: n / n
  - InfoQ: n / n
  - The Hacker News: n / n
  - IPA: n / n
- 過去との重複で落とした候補: (見出しと、どの日の何と重なったか)
- 続報として採用したもの: (見出しと、何が新しいか)
- ⭐の次点と、選ばなかった理由: (1行)
- 使ったトークン量(分かれば):
- 困ったこと・手順どおりにできなかったこと:
```

初日だけ、`run-log.md` の先頭に次も書いてください。

- 実行環境: OS、`bash --version` と `git --version` の1行目、タイムゾーンの既定値
- スケジュールの設定方法(毎朝 06:30 JST をどう指定したか)
- push の方法(どの認証で、承認なしで push できる設定か)

## 合格条件(7日分をまとめて Claude Code が評価します)

| # | 見るもの | 合格 |
|---|---|---|
| 1 | 時刻どおりの完走 | 7日中7日、06:55 JST までに push。人の操作(承認を含む)0回 |
| 2 | 規則 | check.sh が7日とも PASS。URL を整えた上での重複が0件。同じ話題の再掲が、続報を除いて0件 |
| 3 | 取りこぼし | その日の公式版の⭐と同じ話題を載せた日が5日以上 |
| 4 | 探す範囲 | 7日間で1度も採用のない主要信頼ソースが4つ以下 |
| 5 | 鮮度 | 採用記事のうち、公開から2日以内が7割以上(7日の合計) |
| 6 | 正確さ | 毎日3本、計21本を元記事と照合して、数字・固有名詞の食い違いが0件 |
| 7 | 空の欄 | 公式版に採用があるのに「本日の更新なし」とした欄が、7日で2回以下 |

1 を満たせなければ、中身が良くても引き継ぎは見送ります。うまくいかなかった日は、隠さずに `run-log.md` に書いてください。失敗の記録も評価の材料です。
